# Trigger.dev v4.5.4 on Coolify v4 with Traefik — **Split** Webapp & Worker

This README explains how to deploy **Trigger v4** using **Coolify v4** with **Traefik**, separating the **Webapp** and the **Worker/Supervisor**. It also considers an existing **External Docker Registry**.

> Based on the official Trigger.dev `v4.5.4` Docker Compose template and adapted for Coolify (without `ports:` and leveraging **Magic Env Vars** like `SERVICE_FQDN_*` and `SERVICE_PASSWORD_*`). Webapp, supervisor, SDK, build and CLI must use the same release line.

---

## 🧱 Prerequisites

- **Coolify v4** with **Traefik** active.
- Server (Webapp) and (Worker) added in Coolify and **Healthy**.
- **DNS** pointing to the Webapp server (for the Webapp domain).
- **External Docker Registry** operational, with credentials.
- (Optional) Wildcard domain in Coolify for automatic FQDNs.

---

## 🚀 Architecture Overview

- **Webapp**: exposed to Internet via Coolify's Traefik. Manages UI, API, worker group tokens, etc.
- **Worker (Supervisor)**: **not** publicly exposed. Connects **outbound** to the Webapp via HTTPS (`TRIGGER_API_URL`) and executes workloads in ephemeral containers via Docker.
- **Webapp internal services**: Postgres, Redis, ElectricSQL, S2 Lite (Realtime Streams v2), ClickHouse 26.2 (metrics), MinIO (object storage). ClickHouse uses the official image and version against which Trigger.dev develops and tests the v4.5 platform.

---

## 🧩 Quick Steps

1. **Create "Docker Compose (Raw)" resource** in Coolify for the **Webapp** and paste the **`webapp`** YAML below. ClickHouse defaults to `CLICKHOUSE_STORAGE_INIT_MODE=fresh`; legacy Bitnami data is preserved but not copied unless migration is explicitly enabled.
2. In the webapp resource **Environment**:
   - Generate secrets with Magic Vars (`SERVICE_PASSWORD_*`) or paste your own values.
   - Fill in **External Registry** credentials (`DEPLOY_REGISTRY_*`) if you'll use deploys from the Webapp.
   - For bundled s2-lite, keep `REALTIME_STREAMS_S2_ACCESS_TOKEN=ignored`, `REALTIME_STREAMS_S2_SKIP_ACCESS_TOKENS=true` and `TRIGGER_RUNNER_NETWORK=supervisor`.
3. **Deploy** Webapp and configure the **domain** generated by `SERVICE_FQDN_WEBAPP_3000` as `APP_ORIGIN/LOGIN_ORIGIN/API_ORIGIN` (already in the YAML).
4. In the Webapp log, check for the `TRIGGER_WORKER_TOKEN` (shown once). Copy the token.
5. Create a **Docker Compose (Raw)** resource for the **Worker**, paste the **`worker`** YAML below and set in Environment:
   - `TRIGGER_API_URL=https://your-webapp-domain`
   - `OTEL_EXPORTER_OTLP_ENDPOINT=https://your-webapp-domain/otel`
   - `TRIGGER_WORKER_TOKEN=<copied-token>`
   - `MANAGED_WORKER_SECRET=<same as in Webapp>`
   - `TRIGGER_RUNNER_NETWORK=supervisor` (the same Docker network created by Webapp/S2)
6. **Deploy** Worker. Verify in the Webapp that the worker appears as **online**.

The bundled `http://s2/v1` endpoint requires Webapp and Worker to run on the same Docker host. Deploy Webapp first: its Compose stack creates the attachable `supervisor` network. The Worker consumes that network as external, and its task containers join it through `DOCKER_RUNNER_NETWORKS`. S2 remains private. For workers on another host, use hosted S2 or a protected private/overlay endpoint; do not expose token-skipping s2-lite directly to the Internet.

## 🔐 Secrets with **Magic Env Vars** (Coolify)

- Use `SERVICE_PASSWORD_SESSION`, `SERVICE_PASSWORD_MAGIC`, `SERVICE_PASSWORD_ENCRYPTION`, `SERVICE_PASSWORD_MANAGEDWORKER`, `SERVICE_PASSWORD_POSTGRES`, `SERVICE_PASSWORD_MINIO`, `SERVICE_PASSWORD_64_CLICKHOUSE`, etc.
- Coolify generates them once per resource and **maintains** the same value between deployments (useful so sessions/tokens don't get invalidated accidentally).
- You can substitute them with your own values if you prefer.

## 🧪 Quick Checks

- **Webapp**: open `https://<your-FQDN>` → create initial account → check the log for the magic email link.
- **Logs**: if Worker doesn't connect, check `TRIGGER_API_URL`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `TRIGGER_WORKER_TOKEN` and that the server has Internet access.
- **Sessions API**: an unauthenticated `curl -i -X POST https://<your-FQDN>/api/v1/sessions -H 'Content-Type: application/json' --data '{}'` must return JSON `401`, not HTML `404`.
- **Realtime API**: an unauthenticated `curl -i https://<your-FQDN>/realtime/v1/sessions/test/out` must return an API authorization/not-found response, not the dashboard HTML page.
- **S2 runner DNS**: a task container must resolve `s2` on the network named by `TRIGGER_RUNNER_NETWORK`; `getaddrinfo EAI_AGAIN s2` normally means Webapp/S2 and the runner do not share that Docker network. The Webapp deployment must create this network before deploying the Worker.

## 🔄 Upgrade from v4.4.4

Trigger.dev `v4.5.4` removes the legacy v3 engine. Inventory any v3 tasks sharing this tests instance and migrate them before upgrading.

ClickHouse storage has two explicit modes:

- `fresh` (default): starts ClickHouse 26.2 on `clickhouse-data-v26-2` without copying historical ClickHouse data. The legacy `clickhouse-data` volume remains mounted read-only and untouched. Use this mode to validate the upgraded stack without needing duplicate-dataset disk space.
- `migrate-bitnami`: performs the guarded offline copy described below. It requires `CLICKHOUSE_MIGRATION_ACK=offline-copy-confirmed` and sufficient free space.

For the initial fresh validation, set `CLICKHOUSE_STORAGE_INIT_MODE=fresh`, remove `CLICKHOUSE_MIGRATION_ACK`, stop the Worker and previous Webapp stack, then deploy. Trigger.dev recreates its ClickHouse-side schema, but historical ClickHouse metrics and event/trace observability will not appear in the fresh database.

Fresh initialization writes a marker into the new target so later deployments can distinguish it from a partial migration. If you later choose to migrate history, the migration target must be empty. Stop the stack, optionally snapshot the fresh target, then recreate **only** `clickhouse-data-v26-2` or select a new target volume name; never delete or overwrite the legacy `clickhouse-data` volume.

### Optional Bitnami history migration

1. Back up PostgreSQL and take a snapshot or backup of the existing `clickhouse-data` volume. PostgreSQL backups do not include ClickHouse metrics, trace/event history or ClickHouse-side run observability.
2. In the existing ClickHouse terminal, record the current version and table/part counts, and confirm that the actual default disk is under `/bitnami/clickhouse/data`. Also record the legacy container image ID/digest on the Docker host so storage rollback remains reproducible:

   ```sql
   SELECT version();
   SELECT name, path FROM system.disks;

   SELECT
     database,
     table,
     count() AS active_parts,
     sum(rows) AS rows,
     sum(bytes_on_disk) AS bytes
   FROM system.parts
   WHERE active AND database = 'trigger_dev'
   GROUP BY database, table
   ORDER BY database, table;
   ```

3. Ensure the Docker host has enough free space for the complete ClickHouse copy plus at least 33% additional headroom for merges. Treat the migrator's reported minimum as a hard floor and keep several additional GiB free for Docker images and runtime growth.
4. Prepare the updated recipe in the **same Coolify resource** so `clickhouse-data` resolves to the existing named volume, but do not deploy it yet. Keep every existing `SERVICE_PASSWORD_*` value unchanged and set `CLICKHOUSE_STORAGE_INIT_MODE=migrate-bitnami` plus `CLICKHOUSE_MIGRATION_ACK=offline-copy-confirmed`.
5. Drain active runs, stop the Worker/Supervisor and then stop the complete Webapp stack, including the legacy ClickHouse container. The first ClickHouse copy must be performed offline; `depends_on` alone does not make a live physical copy safe.
6. Deploy the prepared Webapp recipe and wait for `clickhouse-migrate` to finish successfully. It copies `/bitnami/clickhouse/data` from the legacy volume into the standard official-image layout in the new `clickhouse-data-v26-2` volume, without modifying the source. It validates the source layout, available space and copied file counts/sizes, replaces only Bitnami's incompatible `tmp` symlink in the clone, and refuses to overwrite a non-empty destination.
7. Confirm that ClickHouse reports version `26.2.19.43`, exposes the required input setting, and has no missing `trigger_dev` tables or lower row counts than the baseline. Active part counts and bytes can legitimately change after merges:

   ```sql
   SELECT version();

   SELECT count()
   FROM system.settings
   WHERE name = 'input_format_json_infer_array_of_dynamic_from_array_of_different_types';

   SELECT
     database,
     table,
     count() AS active_parts,
     sum(rows) AS rows,
     sum(bytes_on_disk) AS bytes
   FROM system.parts
   WHERE active AND database = 'trigger_dev'
   GROUP BY database, table
   ORDER BY database, table;
   ```

   The second query must return `1`.
8. Confirm that `webapp`, `s2-init` and `s2` start successfully and that the Webapp healthcheck passes. New Webapp logs must no longer contain ClickHouse error code `115` (`UNKNOWN_SETTING`).
9. Update and deploy the Worker recipe with the same `v4.5.4` release.
10. Redeploy the Trigger.dev tasks using CLI `4.5.4`.
11. Run both Sessions/Realtime checks above and then retry the iCOne assistant.

The old `clickhouse-data` volume remains unchanged for rollback. Do not delete it after the first successful deployment. A rollback to it will not contain metrics or run activity written after the migration.

Trigger.dev's proposed upstream self-host migration reuses the Bitnami volume in place and adds `data-paths.xml` so ClickHouse 26.2 reads the legacy `data/` subdirectory. This recipe deliberately copies the contents of that subdirectory into a separate volume using the official image's standard layout. Therefore it does not mount `data-paths.xml`, and the original volume remains an untouched rollback source.

After the migration succeeds, remove `CLICKHOUSE_MIGRATION_ACK` from the Coolify environment. Leave `CLICKHOUSE_STORAGE_INIT_MODE=migrate-bitnami`; subsequent deployments use the completion marker and do not repeat the copy.

The preserved volume is a **ClickHouse storage rollback**, not a complete Trigger.dev rollback. Trigger.dev `v4.5.4` cannot remain connected to the old ClickHouse version. A complete rollback can also require the previous Webapp recipe and the matching PostgreSQL backup; never point the legacy ClickHouse image at `clickhouse-data-v26-2`.

Do not roll the Webapp back to `v4.4.4` after its database migrations have run unless the corresponding Trigger.dev rollback procedure explicitly supports it. Redis-backed Realtime Streams v1 does not support Sessions or `chat.agent`; this recipe must remain on S2-backed v2 for the iCOne assistant.

## 🐞 Troubleshooting

- **Worker doesn't appear online**:
  - Check `TRIGGER_WORKER_TOKEN` (no spaces or line breaks).
  - Verify `TRIGGER_API_URL` and `OTEL_EXPORTER_OTLP_ENDPOINT` (valid HTTPS).
  - Ensure Internet access from the Worker server.
- **Build/pull errors for run images**:
  - Configure `DOCKER_REGISTRY_*` in Worker and do `docker login` if using private images.
- **Email login links**:
  - If you don't configure provider (`EMAIL_TRANSPORT`), magic links stay in Webapp logs.
- **Changed `SESSION_SECRET`**:
  - Existing sessions will be invalidated. Avoid in production.
- **ClickHouse `UNKNOWN_SETTING` code 115**:
  - Trigger.dev `v4.5.4` requires `input_format_json_infer_array_of_dynamic_from_array_of_different_types`, available from ClickHouse 25.8. The archived `bitnamilegacy/clickhouse:latest` image is too old and must not be restored as the active service.
- **`clickhouse-migrate` refuses a non-empty target**:
  - This is a safety check. Inspect `clickhouse-data-v26-2` and verify whether a previous migration already completed before taking further action. If a failed partial copy left no completion marker, preserve the legacy source and recreate **only** the new `clickhouse-data-v26-2` volume, or select a new target volume name. Never delete or overwrite `clickhouse-data`.
- **`clickhouse-migrate` reports insufficient free space**:
  - No copy has started yet. Free more than the reported difference and retain several additional GiB for image layers and runtime growth; never use `docker system prune --volumes` because it can remove database volumes.
- **Sessions report missing S2 credentials**:
  - With bundled s2-lite, set `REALTIME_STREAMS_S2_SKIP_ACCESS_TOKENS=true` and the required non-empty dummy `REALTIME_STREAMS_S2_ACCESS_TOKEN=ignored`; then redeploy Webapp.
- **Task reports `getaddrinfo EAI_AGAIN s2`**:
  - Confirm Webapp and Worker are on the same Docker host, deploy Webapp first, verify both use the same `TRIGGER_RUNNER_NETWORK`, and check that the `s2` container plus runner container are attached to that network. Do not publish unauthenticated s2-lite as a workaround.
- **`network supervisor declared as external, but could not be found`**:
  - Deploy the updated Webapp stack first; it owns and creates the attachable network. Then deploy the Worker, which intentionally references the same network as external. If Webapp is already deployed, verify it with `docker network inspect supervisor` before retrying Worker.
- **CORS/origins**:
  - Always use the same domain in `APP_ORIGIN/LOGIN_ORIGIN/API_ORIGIN` (in this README they're derived from `SERVICE_FQDN_WEBAPP_3000`).

## 📎 Notes

- This README assumes a **split setup**. The Worker has no shared volume and receives `TRIGGER_WORKER_TOKEN` explicitly instead of reading the Webapp's bootstrap token file.
- If everything runs on the same Docker host and project, mount the Webapp's `shared` volume in the Worker and use `TRIGGER_WORKER_TOKEN=file:///home/node/shared/worker_token`.
